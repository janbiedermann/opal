# ECMA2024: modernizing `opal/corelib` and `opal/runtime`

Pass over every file of `opal/corelib` and `opal/runtime`, method by method,
looking for JavaScript that can move to the ES2024 target (AGENTS.md: current
and previous Chrome, Firefox, Safari, Node.js 22) for **smaller code** and
**higher speed**. One commit per file or per coherent change; every step is
verified with the full suite on Node, Chrome and Firefox plus lint.

Method of work — same as `IMPROVEMENTS.md`:

* one file at a time, one method at a time;
* measure before/after for every method touched (per-method ns/call harness +
  `node tasks/codesize.mjs --current` for size);
* revert anything that measures slower;
* after every modified file: `sh tmp/check.sh` (node suites + Chrome + Firefox
  + lint) must be green;
* one commit per file.

Baselines (this checkout, `d98e425dd` + the eslint ecmaVersion bump):

## The construct table — measured inside Opal, not in a clean V8

**The single most important finding of this pass.** A construct benchmark run
in a fresh Node process gives the *wrong answer* for this codebase, because
`opal/corelib/array.rb` and `opal/corelib/string.rb` add ~147 and ~120 methods
to `Array.prototype` / `String.prototype`, and V8 drops its fast paths for
several builtins once those prototypes are "tampered" (the codebase already
knows this for `shift`: see the comment at `opal/corelib/array.rb:14-22`).

Bisected with `tmp/bisect-spread.sh` + `tmp/corelib-perf/spread-bisect.cjs`:
loading `opal/base` leaves a plain `[...a, ...b]` at 118 ns, loading
`corelib/array` takes the same site to 1868 ns while `a.concat(b)` stays at
144 ns. Same arrays, same isolate, same benchmark function.

So the authoritative table is measured **inside the Opal runtime**, with the
real tampered prototypes and Opal-built arrays:
`tmp/corelib-perf/es2024-opal-probe.rb`, `tmp/corelib-perf/array-copy-probe.rb`
(ns/call, best of 5 trials, stable over 3 runs, node 22; the clean-V8 column is
`tmp/corelib-perf/es2024-bench*.mjs` on node 22 / node 26 and is kept only to
show how far off it is).

| construct | inside Opal | verdict | clean V8 said |
|---|---|---|---|
| `a.slice(0)` (n=100) | 99 ns | baseline | - |
| `[...a]` (n=100) | 1830 ns | **18x slower than slice** | 0.6x slower |
| `a.concat(b)` (n=100+100) | 312 ns | baseline | - |

Rules this pass follows from that table:

1. **Never convert `concat`/`slice` to array spread** in corelib: past ~10
   elements the spread is 7-18x slower there. Spread is only worth it when it
   removes an *intermediate* array on a small list (see `$prepend_ary`,
   `own_ancestors`, both measured end to end).
2. **Object spread is a real win** (1.9x) - `Object.prototype` is untouched.
3. **The ES2023 copy-then-modify array methods (`toSorted`, `toSpliced`) are
   wins** because they skip the tampered `slice`; `toReversed` is not.
4. **`String#replaceAll` is a 6x win** wherever the pattern is a literal
   string, because `String#replace` lost its fast path.
5. `includes`/`hasOwn`/`at` stay out: `includes` and `at` change or lose
   semantics (SameValueZero answers `true` for `NaN`, Ruby's `==` says false),
   and `hasOwn` is neutral.

## runtime/class.rb, runtime/module.rb (commit 6b3322228)

* `Opal.klass_def` / `Opal.module_def`: `body(klass, [klass].concat(parent_nesting))`
  → `body(klass, [klass, ...parent_nesting])`. The opal/mini bundle holds 138
  class/module definitions, most with a two-argument body. Inside Opal a spread
  of these 1-3 element arrays is perf-neutral (see the construct table), so this
  is kept for the size win and the one allocation it removes; the effect on boot
  time is below the ±2 ms noise of `tmp/boot-time.sh`.
* `typeof Promise !== 'undefined' && ret && typeof ret.then === 'function'` →
  `ret && typeof ret.then === 'function'`: the thenable duck-type stays (a
  non-Promise thenable must still be awaited), only the capability guard goes.
* `Opal.klass`: `(!superclass.hasOwnProperty || (superclass.hasOwnProperty &&
  !superclass.hasOwnProperty('$$is_class')))` → the inner test is redundant.
  Kept the `!superclass.hasOwnProperty` guard: a null-prototype superclass has
  no such method and the original code treats it as "not an Opal class".

## corelib/array.rb (commit 633c16787)

| change | why |
|---|---|
| `Array#sort`: `self.slice(0).sort(cmp)` → `self.toSorted(cmp)` | `toSorted` does the copy and the sort in one call; `Array#slice` is one of the builtins that lost its V8 fast path when `Array.prototype` was tampered |
| `Array#sort!`: `self.slice(0).sort(...)` → `self.sort(...)` behind a `length > 1` guard | the old body copied with `slice(0)` and then let `Array#sort` copy *again*; writing the result back keeps `self` untouched when the comparison fails, as before |

Tried and reverted (all measured with the same harness):

* `Array#+`: `self.concat(other)` → `[...self, ...other]` - 294 → 2069 ns,
  **7x slower**, because a spread of a 100-element array runs on V8's generic
  iterator path once `Array.prototype` is tampered.
* `Array#*`: `result = result.concat(converted)` → `fast_push` in a loop -
  35140 → 66127 ns, **1.9x slower**, even though it copies 15x fewer elements.
* `Array#rotate`: `slice(idx).concat(slice(0, idx))` → spread - 9068 → 10750 ns.
* `Array#reverse` → `toReversed()`: 710 ns (index loop) vs 8110 ns.
* `Array#include?` → `includes`: the loop compares with Ruby `==` (`$eqeq`), so
  `includes` is not equivalent (SameValueZero answers `true` for `NaN`); and
  `Array#index`/`rindex` need the index anyway.

## runtime: irb.rb, helpers.rb, method.rb, send.rb, string.rb, platform_support.js
`typeof x === 'undefined'` where `x` is a property read or a declared parameter
becomes `x === undefined` (10 bytes each, same test): `Opal.eval`/`Opal.compile`
in irb.rb, `value.$$class` in `Opal.inspect`, `obj.$$prototype` in `Opal.alias`,

(`typeof value.$inspect !== 'function'`, `typeof str === 'string'`).

## Runtime files triaged with no change

* `runtime/hash.rb`: the `typeof key === "string" || …` chain repeated in
  `hash_put/hash_get/hash_delete` is a size target (~110 bytes × 8), but a

## What this pass did not change, and why

* `Object.hasOwn` everywhere: neutral inside Opal (94 vs 93 ns), and boot.js
  already binds `$has_own`.
* `Array#includes` for `Array#include?`/`index`: not equivalent (Ruby `==` vs
  SameValueZero, which answers `true` for `NaN`).
* `toReversed`, `flat`, `filter`, `findLastIndex`, `Object.groupBy`, `matchAll`,
  `copyWithin`, `with()`, `Object.entries` iteration, `push(...arr)`,
  `Array.from` copies: all measured slower than the existing loop or `slice`
  inside Opal (table above).
* Arrow functions for the hand-written `function () {}` literals: creation costs
  15.4 ns vs 12.5 ns, so it is a size-only change across ~500 sites with a
  `this`-audit risk; not taken.
* `Error.captureStackTrace` for `Kernel#caller` (currently ~330 µs per call):
  the biggest single hot spot found, but the API is V8-only and it needs an
  engine split, so it is left as a lead rather than folded into this pass.
