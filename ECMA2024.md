# ECMA2024: modernizing the JavaScript of Opal

Two passes are recorded here: the runtime (`opal/corelib`, `opal/runtime`, the
first nine sections) and the toolchain (`lib/opal/potch`, `lib/opal/compiler`,
the last section).

## Pass 1 — runtime

Pass over every file of `opal/corelib` and `opal/runtime`, method by method,
looking for JavaScript that can move to the ES2024 target (AGENTS.md: current
and previous Chrome, Firefox, Safari, Node.js 22) for **smaller code** and
**higher speed**. One commit per file or per coherent change; every step is
verified with the full suite on Node, Chrome and Firefox plus lint.

Method of work — same as `IMPROVEMENTS.md`:

* one file at a time, one method at a time;
* measure before/after for every method touched (per-method ns/call harness +
  `node tasks/codesize.mjs --current` for size);
* revert anything that measures slower;
* after every modified file: `sh tmp/check.sh` (node suites + Chrome + Firefox
  + lint) must be green;
* one commit per file.

Baselines (this checkout, `d98e425dd` + the eslint ecmaVersion bump):

|---|---:|---:|---:|---:|
| opal/base | 832.28 kB | 175.71 kB | 127.56 kB | 39.41 kB |

## The construct table — measured inside Opal, not in a clean V8

**The single most important finding of this pass.** A construct benchmark run
in a fresh Node process gives the *wrong answer* for this codebase, because
`opal/corelib/array.rb` and `opal/corelib/string.rb` add ~147 and ~120 methods
to `Array.prototype` / `String.prototype`, and V8 drops its fast paths for
several builtins once those prototypes are "tampered" (the codebase already
knows this for `shift`: see the comment at `opal/corelib/array.rb:14-22`).

Bisected with `tmp/bisect-spread.sh` + `tmp/corelib-perf/spread-bisect.cjs`:
loading `opal/base` leaves a plain `[...a, ...b]` at 118 ns, loading
`corelib/array` takes the same site to 1868 ns while `a.concat(b)` stays at
144 ns. Same arrays, same isolate, same benchmark function.

So the authoritative table is measured **inside the Opal runtime**, with the
real tampered prototypes and Opal-built arrays:
`tmp/corelib-perf/es2024-opal-probe.rb`, `tmp/corelib-perf/array-copy-probe.rb`
(ns/call, best of 5 trials, stable over 3 runs, node 22; the clean-V8 column is
`tmp/corelib-perf/es2024-bench*.mjs` on node 22 / node 26 and is kept only to
show how far off it is).

| construct | inside Opal | verdict | clean V8 said |
|---|---|---|---|
| `a.slice(0)` (n=100) | 99 ns | baseline | - |
| `[...a]` (n=100) | 1830 ns | **18x slower than slice** | 0.6x slower |
| `a.concat(b)` (n=100+100) | 312 ns | baseline | - |
| `[...a, ...b]` (n=100+100) | 2400 ns | **7.7x slower** | 3.3x *faster* |
| `a.concat(b)` (n=5+5) | 282 ns | baseline | - |
| `[...a, ...b]` (n=5+5) | 289 ns | neutral | 3.3x faster |
| `a.concat([x])` (n=5) | 211 ns | baseline | - |
| `[...a, x]` (n=5) | 258 ns | 1.2x slower | 3.8x faster |
| `a.slice(0).sort(cmp)` | 13300 ns (Array#sort) | baseline | - |
| `a.toSorted(cmp)` | 4390 ns (Array#sort) | **3.0x faster** | 1.06x faster |
| `a.slice(0).splice(i,0,x)` | 10930 ns (n22) / 2031 ns (n26) | baseline | - |
| `a.toSpliced(i,0,x)` | 8095 ns (n22) / 6521 ns (n26) | **1.35x faster on n22, 3.2x slower on n26** - not adopted | 1.66x faster |
| `a.slice(0).reverse()` | 3200-11700 ns (noisy) | baseline | - |
| `a.toReversed()` | 8110 ns | not a win | 0.7x |

| `a.at(-1)` | 129 ns | slower than `a[a.length - 1]` (105 ns) | 1.15x faster |
| `r.push.apply(r, b)` | 216 ns | faster than a push loop (492 ns) | 0.56x |

| `s.matchAll(re)` | 775 ns | 3.5x slower | 0.4x |

Rules this pass follows from that table:

1. **Never convert `concat`/`slice` to array spread** in corelib: past ~10
   elements the spread is 7-18x slower there. Spread is only worth it when it
   removes an *intermediate* array on a small list (see `$prepend_ary`,
   `own_ancestors`, both measured end to end).
2. **Object spread is a real win** (1.9x) - `Object.prototype` is untouched.
3. **The ES2023 copy-then-modify array methods (`toSorted`, `toSpliced`) are
   wins** because they skip the tampered `slice`; `toReversed` is not.
4. **`String#replaceAll` is a 6x win** wherever the pattern is a literal
   string, because `String#replace` lost its fast path.
5. `includes`/`hasOwn`/`at` stay out: `includes` and `at` change or lose
   semantics (SameValueZero answers `true` for `NaN`, Ruby's `==` says false),
   and `hasOwn` is neutral.

## runtime/class.rb, runtime/module.rb (commit 6b3322228)

* `Opal.klass_def` / `Opal.module_def`: `body(klass, [klass].concat(parent_nesting))`
  → `body(klass, [klass, ...parent_nesting])`. The opal/mini bundle holds 138
  class/module definitions, most with a two-argument body. Inside Opal a spread
  of these 1-3 element arrays is perf-neutral (see the construct table), so this
  is kept for the size win and the one allocation it removes; the effect on boot
  time is below the ±2 ms noise of `tmp/boot-time.sh`.
* `typeof Promise !== 'undefined' && ret && typeof ret.then === 'function'` →
  `ret && typeof ret.then === 'function'`: the thenable duck-type stays (a
  non-Promise thenable must still be awaited), only the capability guard goes.
* `Opal.klass`: `(!superclass.hasOwnProperty || (superclass.hasOwnProperty &&
  !superclass.hasOwnProperty('$$is_class')))` → the inner test is redundant.
  Kept the `!superclass.hasOwnProperty` guard: a null-prototype superclass has
  no such method and the original code treats it as "not an Opal class".

## corelib/array.rb (commit 633c16787)

| change | why |
|---|---|
| `Array#sort`: `self.slice(0).sort(cmp)` → `self.toSorted(cmp)` | `toSorted` does the copy and the sort in one call; `Array#slice` is one of the builtins that lost its V8 fast path when `Array.prototype` was tampered |

## What this pass did not change, and why

* `Object.hasOwn` everywhere: neutral inside Opal (94 vs 93 ns), and boot.js
  already binds `$has_own`.
* `Array#includes` for `Array#include?`/`index`: not equivalent (Ruby `==` vs
  SameValueZero, which answers `true` for `NaN`).
* `toReversed`, `flat`, `filter`, `findLastIndex`, `Object.groupBy`, `matchAll`,
  `copyWithin`, `with()`, `Object.entries` iteration, `push(...arr)`,
  `Array.from` copies: all measured slower than the existing loop or `slice`
  inside Opal (table above).
* Arrow functions for the hand-written `function () {}` literals: creation costs
  15.4 ns vs 12.5 ns, so it is a size-only change across ~500 sites with a
  `this`-audit risk; not taken.
* `Error.captureStackTrace` for `Kernel#caller` (currently ~330 µs per call):
  the biggest single hot spot found, but the API is V8-only and it needs an
  engine split, so it is left as a lead rather than folded into this pass.

# Pass 2 — toolchain: `lib/opal/potch` and `lib/opal/compiler`

The same sweep over the 13,233 lines of the compiler and the 27,484 lines of
potch (the JS port of Prism, which assembles into the 21,808-line
`potch.mjs`). Two things differ from the runtime:

* **the prototype trap does not apply — except when it does.** The toolchain
  runs in Node, where `Array.prototype` is untouched, so the clean-V8 table is
  the right one for a build. But Opal compiles itself in the browser (the REPL,
  `opal-parser`), and there corelib *is* loaded, so the same file runs against
  tampered prototypes. The conservative rule held in both passes: no array
  spread for long arrays, no `[...a]` copies.
* **the metric is compile time, not ns/call** — and the emitted JS is a second
  invariant: a modernization refactor must emit byte-identical output.

## Rejected in the toolchain

| construct | why |
|---|---|
| `toSorted` | every `.sort()` here already runs on a freshly built array (`[...set].sort()`, `readdirSync().sort()`, a local `out.sort()`), where sorting in place is strictly cheaper than copying and sorting. The one site that sorts an array it did not create, `builder/cache.mjs:34`, would turn a correct fix (stop mutating the caller's array) into a slower one. |
| `at(-1)` | 8 sites (`stack[stack.length - 1]` and friends), all cold, and `at` measured 0.92x on node 26. |
| `Object.hasOwn` | the two `Object.prototype.hasOwnProperty.call` sites guard `this.options`, a user-supplied object; the call form is the right one there and `hasOwn` is not faster. |
| `forEach` → indexed `for` | 23 sites, all with an index. The closures they allocate never reach the top of the heap profile, so the rewrite trades readable code for nothing measurable. |
| array spread | same rule as pass 1: this code also runs in a browser with corelib loaded. |

## Deliberately out of scope: the emitted code

`cli/exe_compiler.mjs` emits `Object.assign({}, process.env, {...})` and `var`
into an executable's HTTP helper, and `nodes/collections.mjs` emits
`[].concat(...)` for array literals with splats. Modernizing *emitted* code is
a different change class: it moves the compiler fixtures and ruby/spec, and the
`[].concat(...)` case must stay — generated code runs against the tampered
`Array.prototype` that pass 1 measured, where spread is 8-10x slower at n=100.

## Follow-up: the DCE directives and the census slice

Items 1 and 3 of the allocation list, implemented.

**The DCE directives.** `--dce` is opt-in (`Builder` defaults `dce = false`),
but the compiler emitted a directive for every method definition and every
helper use regardless, and nothing read them: `Directive.code` is `""`, so
`codeOf` adds nothing and the source map skips it. Now:

* `Compiler` gained a `dce` option (default false) and `isDce`; the builder
  sets it beside `cache_fragments`, which it already coupled to DCE.
* `dceDefBegin` / `dceDefEnd` / `dceUse` return `null` when DCE will not run,
  before building their params.
* `Base#push` and `Base#unshift` drop nullish entries.

The first version returned one shared frozen `Directive("", {})` instead. That
was the wrong shape: it left 104,963 `Directive` instances in the fragments
arrays of a compile DCE would never read, so `frag instanceof Directive`
stopped answering "is there a directive here". The switch has to be all the way
off. Dropping the null in `push`/`unshift` covers the 20 call sites in the six
node files without repeating a condition at each one, and a `Directive` in a
fragments array now always means a directive something will consume.
`Scope#toVars` is the exception: it assembles a plain array, so its two sites
test the result themselves.

`codeOf`, `eachFragment`, `flatten` and `lastFragment` already skipped nullish
entries; `SourceMap#generatedCode` and `#mappings` do not - they walk
`this.fragments` with a raw `forEach` and read `fragment.code` - which is why
the null is dropped at the push instead of being allowed into the array.

`helper()` and `wrapWithPostprocessorDirectives()` keep a guard of their own.
That is a fast path and not the mechanism, and it pays: with the two guards
removed, compile time rose in 3/3 paired rounds (1358.3 -> 1376.0 ms mean,
-1.3%, and -4.8% of codegen), because the option literals are built before the
helper's own guard is reached.

Exact effect over the 21 files of the identity check: **237,569 `Directive`
objects (each with its params literal, plus a default options object for the
one-argument calls) become none at all** - `tmp/tc-directives.mjs` counts 0
`Directive` instances in the fragments of a DCE-off compile, against 237,569
before.

| measurement | old | new | |
|---|---:|---:|---|
| GC share of compile time (3 paired `--cpu-prof` runs) | 24.62 / 24.32 / 24.21% | 23.81 / 24.04 / 23.46% | lower in 3/3 |
| total compile, min of 5 per round | 1359.30 / 1377.58 / 1371.83 ms | 1340.08 / 1355.99 / 1364.51 ms | faster in 3/3, mean −1.2% |
| `dceUse` + `helper` self-allocated (heap profile) | 5.0 + 2.5 MB | gone from the profile | |

The `--heap-prof` *totals* turned out to be unusable as a measurement: two
runs of the same code reported 138.9 MB and 153.3 MB. The per-site presence
and the exact object count above are the numbers to trust.

**The census slice.** `takeCensus` ran `node.body.body.slice(-2)` for every
`DefNode` with two or more statements, allocating an array to pick two
elements out of one that already existed. Indexed reads replace it.

Measured on its own (`tmp/census-bench.mjs` runs the two census bodies over
the same parsed trees): it avoids **3,238 arrays per compile** and the census
result is identical on every file, but it is not measurable on speed - two
runs of the isolated benchmark gave +0.9% and -2.0%, and the whole census is
only ~40 ms of a ~1350 ms compile. Attributing the table above: HEAD against
HEAD with only this file reverted gives 1349.0 vs 1350.5 ms (mean of three
paired rounds), so the GC and total gains belong to the DCE change alone. The
census slice stays for the 3,238 objects, not for a speed claim.

Two new specs cover it. The builder one needed `cache_fragments: true` forced
on both sides: `RubyProcessor` only attaches `file.compiler` to the processed
file when that option is on, so without it the "DCE off" half of the test
counted nothing and passed against the old code too.
