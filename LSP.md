# Opal Language Server — Implementation Plan

Goal: an LSP server for Ruby code developed **with and for Opal**, living in
`lib/opal/language-server/`, entered by `lib/opal/exe/lsp.rb`, built into
`exe/lsp` (Node program) and `exe/lsp.exe` (single-file executable) exactly like
`exe/ruby` / `exe/gem` / `exe/bundler`. It speaks the Language Server Protocol
as current VS Code speaks it, and its language model is **Opal's Ruby, not
CRuby's**: it analyses, completes and diagnoses against what Opal can actually
parse, compile and run.

Reference implementation: `/root/workspace/ruby-lsp` (Shopify/ruby-lsp
v0.26.11, MIT — same license family as Opal, so code can be copied verbatim
with attribution kept; a NOTICE line goes into the copied files' headers).

## 1. Protocol target

- Spec baseline: **LSP 3.17** (what VS Code's client library implements in
  full) and the **3.18** additions VS Code actually ships: pull diagnostics
  (`textDocument/diagnostic` / `workspace/diagnostic`), `diagnostic.refresh`,
  semantic-tokens full/range, inlay hints, type hierarchy, linked ranges left
  out. The LSP site states 3.18 is `specification-current`; VS Code negotiates
  everything through capabilities, so the plan is: implement 3.17 statically
  registered, plus 3.18 pull diagnostics negotiated when the client asks
  (`textDocument/diagnostic: {}` in `generalCapabilities`).
- Transport: stdio only (JSON-RPC 2.0 with `Content-Length` framing), the same
  transport ruby-lsp uses (`lib/ruby_lsp/utils.rb:310-340`). No socket mode.
- Position encoding: negotiate `utf16` (the default and what VS Code sends).
  This is free in Opal: Ruby strings are boxed JS strings, i.e. UTF-16 code
  units, and Opal's Prism parse locations are UTF-16 code-unit offsets
  (`lib/opal/parser/index.mjs:9-10`). No code-unit caches needed — this is the
  one place where the port is *simpler* than ruby-lsp. Do **not** offer utf8.

Capabilities to advertise (static registration; VS Code supports all of these
without dynamic registration):

| Capability | Phase |
|---|---|
| `textDocumentSync` (incremental, openClose, save) | P1 |
| `diagnosticProvider` (pull, 3.18) ✅ P6 + `publishDiagnostics` (push fallback) ✅ P1 | P1 push / P6 pull |
| `documentSymbolProvider`, `foldingRangeProvider`, `selectionRangeProvider`, `documentHighlightProvider`, `semanticTokensProvider` (full+range), `inlayHintProvider`, `onTypeFormattingProvider` | P2 |
| `definitionProvider`, `referencesProvider`, `renameProvider` (+`prepareProvider`), `workspaceSymbolProvider` | P3 |
| `hoverProvider` ✅, `signatureHelpProvider` (triggers `(`, `,`) ✅, `typeHierarchyProvider` ✅ | P4a |
| `completionProvider` (resolve, triggers `. : @ $`) | P4b |
| `codeActionProvider` (quickfix ✅ P5; refactor.extract), `executeCommandProvider` (`opalLsp/compileToJs`, `opalLsp/showSyntaxTree`) | P5/P7 |

Out of scope for the protocol in v1: formatting/rangeFormatting (no
formatter advertised; deferred delegation to an external CRuby formatter is
revisited once the server works end-to-end — see §9 and §11), documentLink,
notebooks, call hierarchy (later), workDoneProgress (P6), `$/cancelRequest`
honored between chunks (P6).

## 2. What "exactly the Ruby features Opal supports" means

Three gates, in increasing depth, all run inside the server:

1. **Parse gate** — every document is parsed with Opal's own parser
   (`lib/opal/parser`, Prism 1.9 port, grammar set to Ruby 4.0 exactly like the
   compiler, `lib/opal/compiler/compiler.mjs:282`). All `errors`/`warnings`
   from `parseWithMetadata` become diagnostics with exact ranges. Anything
   Opal's parser rejects is flagged; anything it accepts is what every other
   feature (completion, index) works from, so the whole server shares one
   grammar — Opal's.

2. **Compile gate** — on save (compile is heavier than parse, not on every
   keystroke), run `new Compiler(source, {file}).compile()`
   (`lib/opal/compiler/compiler.mjs`) and catch `OpalSyntaxError` (has `file`,
   1-based `line`, 0-based UTF-16 `column`, `sourceLine`); compiler warnings go
   through the `options.warning` callback. This surfaces everything the parser
   accepts but Opal refuses to compile — the "Opal does not support this"
   class: unsupported node rewrites, `unsupported parameter`/`rescue target`,
   back-reference limits (only `$&`, `$'`, `` $` ``, `$+` compile,
   `nodes/variables.mjs:126`), and Ruby regexps that V8 rejects — atomic
   groups `(?>...)` and possessive quantifiers (`docs/unsupported_features.md`,
   AGENTS.md `/x` note). This is the same code path the build will run, so the
   diagnostic is authoritative, not a lint heuristic.

3. **API gate** — a curated `unsupported.rb` feature list (from
   `docs/unsupported_features.md` + `spec/filters/unsupported/`): `Thread.new`,
   `Fiber`, `Data.define`, string bang methods (`<<`, `gsub!`, `tr!`, `[]=`, …
   raise `NotImplementedError`, `opal/corelib/unsupported.rb`), `IO#flock`,
   `Symbol`-vs-String assumptions (`x.is_a?(Symbol)` is true of every String),
   `Array(hash)` semantics, `Integer`/`Float` distinction (both are `Number`),
   requires of stdlib names Opal lacks (a failed require is *silently skipped*
   at runtime per AGENTS.md, so the LSP is the only place that can flag it —
   check the name against the bundled stdlib module table + installed gems).
   Each gate becomes a diagnostic with a source `opal` / code like
   `unsupported.thread`, and where a mechanical fix exists, a **quickfix code
   action**: `msg << x` → `msg += x` (corelib has no mutable `String#<<`),
   `(?>a+)` → `(?:a+)`, `Thread.new {}` → `Promise`/`await` pointer.

Hover, completion and go-to-definition are equally Opal-scoped: the index
contains **Opal's own corelib/stdlib sources** (see §5) plus workspace files —
never CRuby's docs or methods. `String#<<` is not offered; `Array#sum` is
because `opal/corelib/enumerable.rb:1413` has it. Require-path completion
offers only what Opal can load.

## 3. Runtime constraints (the server is Ruby compiled by Opal)

The server itself is Ruby source in the bundle, so it inherits Opal's
limitations and must be written inside them:

- **Single-threaded.** `Thread.new` raises (`stdlib/thread.rb` shim).
  ruby-lsp's reader/worker/outgoing-dispatcher threads (`base_server.rb`)
  collapse into one synchronous loop: `$stdin` → parse frame → dispatch →
  `$stdout`. This is proven to work in a compiled bundle:
  `stdlib/opal-replutils.rb:110-124` is exactly this stdin-loop shape. Long
  work (workspace indexing, compile checks) is chunked with a
  "budget of N files, then check for pending input" pattern; `$/cancelRequest`
  sets a flag consulted between chunks.
- **Byte-exact framing in JS.** LSP `Content-Length` counts UTF-8 bytes; Opal
  strings are UTF-16. The transport is one small file
  (`lib/opal/language-server/transport.rb`) doing the read/write through
  backticks over `process.stdin`/`process.stdout` with `fs.readSync` +
  `TextDecoder('utf-8')` (the AGENTS.md TextDecoder lesson) so framing never
  loses bytes to the string layer. JSON through `stdlib/json.rb` (thin wrapper
  over `JSON.parse`/`JSON.stringify`); message payloads are Hashes with String
  keys — no `symbolize_names` needed if the dispatch reads string keys (ruby-lsp's
  `symbolize_names` symbols are Strings here anyway, Opal `Symbol == String`).
- **Immutable strings / no bang methods**: builders concatenate (`msg += ...`).
- **No `Data`, no `Fiber`**; `Struct`, `Set`, pattern matching, endless methods,
  `Hash#except`, `filter_map`, `sum` are all supported by corelib/Prism —
  ruby-lsp's `lib/` uses none of the missing ones (checked: no `Data.define`,
  no bare `it` outside one file), so most ported code compiles as-is.
- `language_server-protocol` gem is **not needed**: ruby-lsp uses it only for
  `Interface::*` structs and `Constant::*` enums; the port replaces them with
  literal Hashes and integer constants in one file
  (`lib/opal/language-server/protocol.rb`).
- `DidYouMean::JaroWinkler` (used by `Index#fuzzy_search`) gets a small pure
  Ruby implementation (~40 lines) in the indexer.
- No Bundler/Gemfile/RuboCop integration: drop `setup_bundler.rb`,
  `configuration.rb`, formatter support, add-on system. Document links to
  rubygems.org (`package_url.rb`) dropped.

## 4. Server architecture

```
lib/opal/exe/lsp.rb                      # entry: options, --check, start server
lib/opal/language-server.rb              # umbrella require
lib/opal/language-server/
  protocol.rb          # constants (SymbolKind, DiagnosticSeverity, ErrorCodes, ...)
                       # + Message/Notification/Request/Error/Result wrappers (port of utils.rb)
  transport.rb         # stdio framing: fs.readSync stdin, TextDecoder, Content-Length write
  json.rb              # thin: JS JSON.parse/stringify bridge
  server.rb            # lifecycle + request routing (port of server.rb case)
  global_state.rb      # client capabilities, configuration, index handle
  store.rb document.rb ruby_document.rb   # doc sync, incremental edits (UTF-16 only
                                           # scanner — port document.rb dropping
                                           # Utf8/Utf32 scanners)
  prism/
    parser.rb          # require 'opal/parser/index.mjs'; Opal.esm["opal/parser/index"];
                       # envelope cache + line-index (UTF-16 offsets -> LSP Position)
    node.rb            # POJO AST wrapper: type, name, child_nodes, location as
                       # {start_line:, start_column:, ...} + range helpers
    dispatcher.rb      # walk nodes, fire on_<type>_enter/leave (ruby-lsp's
                       # Prism::Dispatcher call shape, so listeners port cheaply)
  indexer/
    entry.rb index.rb visibility_scope.rb prefix_tree.rb reference_finder.rb
                       # ported from ruby_indexer (entry/index/visibility/prefix/reference),
                       # Dispatcher calls re-targeted at prism/dispatcher.rb;
                       # "entries" are record graphs read through one small
                       # accessor module (POJO-backed or Map-backed, §5/§10.6),
                       # so the baked graph and live-indexed workspace files
                       # share one representation and one query path
    driver.rb          # build-time main (§5): indexes corelib/stdlib sources,
                       # writes baked_index.mjs + corelib_sources.mjs;
                       # never required at run time
    baked_index.mjs    # GENERATED (§5): the corelib/stdlib record graph as one
                       # literal (POJO or Map — decided by benchmark, §10.6);
                       # the builder links it verbatim (JsProcessor), V8
                       # allocates it at bundle evaluation — no compile step,
                       # no parsing step, no constructors
    corelib_sources.mjs # GENERATED (§5): path -> source strings, used only to
                       # dump a single file on demand when navigating into
                       # corelib without an opal checkout
    jaro_winkler.rb    # replaces DidYouMean
  listeners/           # ported: document_symbol, folding_ranges, document_highlight,
                       # semantic_highlighting, inlay_hints, definition, hover,
                       # completion, signature_help
  requests/            # one per protocol method (ported structure from ruby_lsp/requests)
  unsupported.rb       # gate 3: curated CRuby-not-in-Opal API table + quickfixes
  keyword_docs.rb      # port of static_docs KEYWORD_DOCS (embed the two md files)
  progress.rb          # window/workDoneProgress + $/progress helpers
```

Key data flow: `didOpen`/`didChange` → `RubyDocument#parse!` calls
`parseWithMetadata(source)` once → `{ast: POJO, comments, errors, warnings,
offsets}`; every listener walks the AST through `prism/dispatcher.rb`;
`RubyDocument#locate(line, char)` is the BFS down `child_nodes` (port of
`ruby_document.rb:25-113` with the code-unit cache removed, since UTF-16
offsets are native). `Document#push_edits` maps LSP `{line, character}` to the
UTF-16 offset via a newline table maintained per parse — and since both LSP
positions and Prism offsets are UTF-16 units, `source[start...end]` on the
unboxed string value is the edit splice. The surrogate-pair trap (AGENTS.md
string-indexing note) is why the splice must go through the JS string value
(`source.valueOf()` + `slice`), not Ruby character indexing; a spec with a
`𠀀` before an edit pins this.

Position/offset conversion is one cached table per document: `envelope.offsets`
gives line starts in UTF-16 units; `position ↔ offset` is a binary search.
Prism error entries carry `{start, end, message, severity}`; the `^~ caret`
rendering code in `spec/lib/parser/support/errors-format.mjs` is *not* wanted —
they go straight to LSP ranges.

## 5. The Opal corelib/stdlib index — built at exe build time, never at run time

The corelib/stdlib index is **not built when the server starts and not cached
in the user's home directory**: it is built when `exe/lsp`/`exe/lsp.exe` are
built, and it travels inside the executable in ready-to-use form.

- **Generator: `tasks/language-server/update_baked_index.mjs`** (a regen task
  like `tasks/compiler/update_fixtures.mjs`). It builds a tiny driver bundle
  (opal/full + `opal/language-server` + `indexer/driver.rb`) into `tmp/`,
  runs it on Node, and the driver indexes the Ruby sources of
  `opal/corelib/**`, `opal/opal/*.rb`, `stdlib/**/*.rb` and `stdlib/opal/*.rb`
  (~2.9 MB, read from the checkout at build time) with the same
  DeclarationListener that indexes workspace files, `collect_comments: true`.
- **Output: two committed generated `.mjs` modules** (the
  `lib/opal/parser/parser.mjs` pattern — committed generated file, a lint
  step/spec regenerates and byte-compares to catch staleness):
  - `lib/opal/language-server/baked_index.mjs` — `export default {…}` with
    the whole entry graph as **plain object/array/string literals**: the
    finished record graph, not code that rebuilds it. The builder's
    JsProcessor links required `.mjs` files verbatim (no Ruby compilation,
    proven by `stdlib/opal-parser.rb`), V8 parses the literal at bundle
    evaluation, terser minifies the whole bundle around it. Startup cost:
    one V8 parse of the literal — no JSON step, no Marshal format, no
    constructors, no hydration.
  - **POJO vs Map — RESOLVED by measurement: POJO ships (§10.6 result: boot
    66.9ms vs 111.9 vs 184.3; the Map forms win only a chained-`get` micro
    loop).** Entries are read
    through one accessor module (`indexer/entry.rb`), so the underlying
    shape is a swappable detail:
    - *POJO* (object/array/string literals, the prism/node.rb idiom): truly
      static allocation — V8 builds the graph from literals with hidden-class
      fast property access; but Ruby has no property access, every field
      read goes through a backtick accessor.
    - *Map*: Opal's `Hash` is itself backed by a JS Map, so a Map graph can
      feed the corelib Hash operations directly (Ruby `[]`/`each`/`key?`
      over the graph without per-field x-strings); cost is eager `Map`
      construction at bundle evaluation and monomorphic-but-generic access.
      Construction has two emitted forms — pair arrays
      (`new Map([[key, value], …])`, compact, allocates one throwaway array
      per entry) vs the chain (`new Map().set(key, value).set(…)`, more
      generated code but no pair arrays, usually faster) — both generated,
      benchmarked on the *real* index, not synthetic probes.
    Generate both from the driver, benchmark the hot paths (initialize boot
    time, `resolve`/`resolve_method`, ancestor linearization, prefix
    completion, record field reads in `hover`/`completion`) in the same
    process, and ship the winner; the accessor module makes the choice a
    one-file swap. Live workspace indexing produces the same records either
    way.
  - `lib/opal/language-server/corelib_sources.mjs` — path → source strings.
    Only used when a user *navigates into* corelib without an opal checkout:
    the server dumps that one file to `~/.cache/opal-lsp/sources/`
    on demand (a real file VS Code can open; no custom URI scheme). No
    startup work, and the cache holds only the files actually opened.
  - `baked_index.mjs` also carries a content digest per indexed file.
- **Server start**: `global_state.rb` grabs the esm export and treats it as
  the immutable base of the `Index` — `[]`, `resolve*`, ancestor
  linearization and the completion prefix trees read it directly. Only
  *workspace* files are indexed at run time. This replaces ruby-lsp's
  `rbs_indexer.rb` (no RBS in Opal).
- **Staleness**: at initialize, if the workspace is an opal checkout
  (`initializationOptions.opalHome`, or detected `opal/corelib`), the server
  compares the baked per-file digests with the on-disk files and re-indexes
  *only changed* corelib/stdlib files through the same listener
  (usually zero edits — init stays fast; navigating into corelib lands in
  the real checkout sources, so corelib development works end-to-end).
  Without a checkout the baked index is the truth, and it is fresh by
  construction because it was generated from the sources that built the exe.
- Hover docs are the real corelib RDoc-style comments, embedded as strings
  in the baked records — no comment re-parsing at run time for corelib.
- The baked records are §2's API gate ground truth: a core-type method call
  is suspect iff its name is not in the baked records for the receiver's
  ancestors (soft warning; hard errors come from the compile gate).

## 6. Build and packaging

Mirrors the `ruby`/`gem`/`bundler` trio exactly:

- `tasks/lsp/bundle.mjs` — `buildLspBundle()`: Builder with
  `dynamic_require_severity: "ignore"`; boot index (`load: true`): `opal`,
  `opal/full`, `thread`, `json`, `set`, `strscan`, `uri`, `pp`,
  `opal/language-server`; requirable-but-eager sweep of
  `lib/opal/language-server/**` via `treeRequireNames` (so a bundle carries
  the whole server even though the program requires it through one file;
  the sweep takes `.rb` — the two generated `.mjs` modules are not swept,
  the server code `require`s them by literal name and JsProcessor links
  them verbatim); `opal-parser` at boot (the compile gate and `compileToJs`
  need the compiler on every keystroke path); `OPAL_COMPILER_KEY` from
  `tasks/ruby/bundle.mjs` (same key, so a future `--check` can share trees);
  then `lib/opal/exe/lsp.rb` + `::Kernel.exit`; terser minify like the
  others (terser also minifies the linked `.mjs` literals inside the bundle).
- No staging in the bundle build: the index is already in the tree as
  `baked_index.mjs` (§5). `node tasks/language-server/update_baked_index.mjs`
  regenerates it and `corelib_sources.mjs`; the diff is reviewed like the
  compiler fixtures, and a freshness check (regenerate to tmp, byte-compare)
  joins `tasks/lint.mjs` next to the `parser.mjs`-matches-its-parts step.
- `exe/lsp.rb` options (hand-parsed like `lib/opal/exe/ruby.rb`, no optparse
  boot cost): `--version` (answers `Opal::VERSION` from `opal/version`,
  which §0 makes one source), `--help`, `--check [DIR]` (batch mode: run
  gates 1–3 over every `*.rb`/`*.rake`/`Gemfile`-ish file under DIR, print
  `file:line:col: severity: message`, exit nonzero on any — this gives CI
  value and a testable entry point without protocol),
  `--log-file PATH` (stderr defaults to quiet; logs never touch stdout),
  `--time-index`.
- `tasks/lsp.mjs` → `exe/lsp` (`#!/usr/bin/env node` + bundle), `OUT` honored.
- `tasks/lsp_exe.mjs` → `exe/lsp.exe` through the shared
  `buildSeaExecutable` (`tasks/sea_exe.mjs`, env flag `OPAL_LSP_EXE_NODE`).
- `package.json`: `build-lsp`, `build-lsp-exe`.

## 8. Testing

- `spec/lib/compiler/lsp_cli.test.mjs` (runs inside the `compiler` suite
  glob; builds the bundle in `before` like `ruby_exe.test.mjs`): spawn
  `exe/lsp` **asynchronously** (AGENTS.md lesson — `spawnSync` deadlocks any
  test that feeds stdin), write framed messages, assert framed responses.
  Cases: initialize handshake + capabilities; didOpen with a syntax error →
  publishDiagnostics range; `didChange` incremental with a **surrogate pair
  (`𠀀`) before the edit** (UTF-16 positions must land correctly); document
  symbol/folding/semantic-tokens golden responses; hover on `String#gsub`
  answers from the baked index (works with an empty workspace — proving no
  startup indexing); go-to-definition into corelib lands in the checkout
  when one is given and in an on-demand-dumped source file otherwise;
  completion lists Opal's methods
  (offers `Array#sum`, not `Hash#compare_by_identity`… verify against a small
  set); `Thread.new` and `msg << x` produce unsupported diagnostics with a
  quickfix; `require "net/http"` produces the missing-stdlib diagnostic;
  `textDocument/diagnostic` pull (P6) returns the same set.
- `--check` mode: fixture tree with known-bad files → exit code + line-stable
  output (no protocol needed — the cheap end-to-end gate test).

  doc comment; signatureHelp finds the innermost call whose `opening_loc`/
  `closing_loc` (the envelope's field names) span the cursor and reports
  the recorded parameters + comma-counted activeParameter; the type
  hierarchy walks recorded superclasses/includes out and scans includes/
  superclasses back. Receiver typing moved into `NavigationTarget
  .method_owner/receiver_class` — shared with definition (and P4b).
  Envelope gotcha: CallNode locs are `opening_loc`/`closing_loc`, not
  `open_loc`/`close_loc` as in Ruby Prism.
- **P4b — completion. ✅ LANDED (2026-10-24).** `textDocument/completion`
  + `completionItem/resolve` (trigger chars `. : @ " '`): `.` completes the
  linearized visible methods of the receiver type (literals, constants,
  `Klass.new.m`); bare capitalized words complete top-level constants,
  `Mod::` its direct children; bare lowercase words complete implicit-self
  methods (inside a class body) plus keywords; `@` the document's own
  instance variables (not indexed); `require "` the real requireable
  feature names derived from the baked digest keys. Items carry a small
  data tag; resolve fills `detail` (Owner#m(params)) and `documentation`
  from the baked record comment. Cap 100 items. Gotcha: an unterminated
  string swallows the rest of the document (InterpolatedStringNode wraps
  the StringNode - completion walks ancestors to find the `require` call,
  and everything *below* an unterminated string is string content).
- **P5 — Opal gates. ✅ LANDED (2026-10-24).** `features/opal_gate.rb`.
  *Compile gate* (on `didSave` only): a real `Opal.esm["opal/compiler/index"]
  .Compiler` pass over the document. A compiler refusal raises
  `OpalSyntaxError` whose POJO `location` (1-based line, 0-based UTF-16
  column, `sourceLine`) becomes a severity-1 `code:"compile"` diagnostic
  spanning the failing source line; refusals without a position land at
  the document start. The Compiler's `warning` callback is collected into
  severity-2 `code:"compile-warning"` diagnostics - its text ends with
  `-- <file>:<line>`, which is parsed back out to give the diagnostic a
  whole-line range (`ParseResult#line_range`), and exact-message dedupe
  keeps the parse gate's warnings single. Honest finding: the current
  Compiler refuses far less than §2 expected (proc-destructuring params,
  anonymous rest/`&`-forward, constant rescue targets, possessive regexes
  all compile clean), so the warning channel carries most of the value:
  the `/o` flag drop, backtick-intent, and x-string-semicolon warnings are
  Opal-only knowledge no parser emits. `didSave` on an unparseable
  document is skipped - the parse diagnostics already on screen stand.
  *API gate* (published with the parse gate on every edit): curated
  severity-2 `unsupported.*` rules on unambiguous shapes only - the
  `Thread`/`Fiber` constants, `Data.define`, bang methods on string
  literals (immutable String), `is_a?/kind_of?/instance_of?(Symbol)` and
  `Symbol === x` (Symbol==String), `require` of stdlib Opal lacks
  (psych/readline/reline/irb/resolv - silently skipped at run time).
  *P5b quickfixes* (`features/code_actions.rb`,
  `codeActionProvider:{codeActionKinds:["quickfix"]}`): recognized by the
  diagnostic's `code` plus its exact range start; three mechanical
  single-edit fixes - drop the bang character (`gsub!`→`gsub`), remove a
  missing-stdlib require call, drop the `/o` flag character (the
  RegularExpressionNode flag list carries `"once"`; the source probe
  deletes the trailing `o` only when a non-word char precedes it).
  Gotchas (in AGENTS.md): x-strings pass backslashes through raw (regexes
  take `\d`, JS string literals still take `"\\"`); an assignment whose
  RHS starts with `#{...}` guarded by an x-string `if` silently swallows
  the following statement.
- **P6 — pull diagnostics & file watching. ✅ LANDED (2026-10-24).**
  `textDocument/diagnostic` answers a full `DocumentDiagnosticReport`
  running all three gates on demand (parse + API always, the Compiler
  pass whenever the source parses) - the same `gate_diagnostics` the
  save-time push uses, so pull and push never disagree. Unknown documents
  answer `{kind:"full", items:[]}`. `diagnosticProvider` advertises
  `interFileDependencies:false, workspaceDiagnostics:false` (the gates are
  per-file claims; a closed-file workspace sweep would need the index to
  carry diagnostics, it does not).
  `workspace/didChangeWatchedFiles` re-indexes Created/Changed `.rb`
  files from disk and removes Deleted ones (`GlobalState
  #index_workspace_file` → `Index#index_source` replaces a file's live
  records whole); open documents are skipped, the editor buffer wins.
  Gotcha: the path decode is JS `#{uri}.slice(7)` - Ruby `uri.slice(7)`
  answers a *single character* (like `[]`), which turned every watched
  path into "/" until the probe read EISDIR.
  *Deferred with reasons:* `$/cancelRequest` stays a no-op - dispatch is
  single-threaded and synchronous, a request either finishes or has not
  started, and the loop already ignores the notification. workDoneProgress

  the client's patience; revisit if the workspace cap ever grows.

## 10. Risks / spikes (first-week resolutions)

1. **Stdin framing** (P0 spike): `fs.readSync(process.stdin.fd)` on a pipe in
   the SEA + node bundle both; partial-read and `EAGAIN` handling; confirm
   `TextDecoder` incremental decode across frame boundaries and that stdout
   writes land whole (ruby-lsp's `sync = true` analogue).
2. **`parse_lex` vs `parse`**: ruby-lsp's `RubyDocument` uses `parse_lex`;
   the JS port has `lexWithMetadata` and `parseWithMetadata(code, options,
   wantTokens)` with token objects. Decision expected: plain parse suffices
   (semantic tokens and on-type-formatting in ruby-lsp are AST+locate driven);
   take tokens only if locate proves insufficient.
3. **Prism POJO API surface** (P2 spike): confirm `convert.mjs` gives every
   listener the fields it needs (`CallNode#name` as String, `ConstantPathNode`
   full name assembly, `child_nodes` generic field walk incl. optional/`nil`
   entries) and write the adapter once.
4. **Bundle size and boot cost**: `exe/gem` is 2.2 MB; `exe/lsp` adds the
   compiler at boot, `baked_index.mjs` (record graph of ~150 corelib/stdlib
   files — a large object literal) and `corelib_sources.mjs` (~2.9 MB of
   source strings) → estimate ~6–8 MB. Measure with `tasks/codesize`-style
   byte counts **and** boot time (`--check` on an empty dir, and the
   initialize latency in `lsp_cli.test.mjs`): V8 parses the literal at
   bundle evaluation, terser spends build time minifying it. Mitigations if
   needed: gzip `corelib_sources.mjs`'s payloads (stdlib zlib inflates them
   on first navigation), index only `opal/corelib` + the stdlib classes
   users actually require, drop the string values from `baked_index.mjs`
   that only `--check` needs.
5. **Compile-gate cost**: full `Compiler#compile` per saved file (corpus
   compile is allocation-bound, AGENTS). Budget it in the P5 chunker; parse
   diagnostics stay on every edit, compile diagnostics only on save/idle.
6. **Record representation: POJO vs Map** (P3 benchmark, §5): one accessor
   module over either shape — generate three `baked_index.mjs` variants,
   the POJO literal and both Map constructions (`new Map([[k, v], …])` with
   its pair-array temporaries, and the `.set()` chain without them), then
   compare on the *real* index: boot (V8 parse + allocation — literals vs
   eager Map construction, the pair-array cost included) and the hot query
   paths (`resolve`/`resolve_method`, ancestor linearization, prefix
   completion, per-field reads in hover/completion), measured in the same
   process per the AGENTS.md measure-inside-the-runtime rule. The Map
   variants trade static literal allocation for direct Ruby-Hash access
   (Opal's `Hash` is Map-backed); the POJO variant trades backtick field
   accessors for hidden-class fast property reads. Ship the winner; swap
   is one file.
   **Result (2026-10-24): POJO.** `tasks/language-server/bench_index.mjs`
   on the real 1.7MB payload (variants emitted by the bake task): boot in
   fresh processes 66.9ms (pojo) / 111.9ms (pair-arrays) / 184.3ms
   (.set-chain), RSS 122/142/158MB; a workspaceSymbol-style sweep of all
   280 modules' method keys ~0.0/0.1/0.1ms. Only the hand-microscopied
   five-deep resolve chain favored Map (69-77ns vs 93ns — megamorphic
   property reads vs monomorphic `Map.get`), which no request runs more
   than a few hundred times. Boot cost repeats at every server start and
   the POJO graph is also what terser shrinks best; the accessor module
   keeps the decision reversible.
7. **Hover comments**: corelib/stdlib comments are baked into the records at
   generation time — nothing re-parsed at run time. For workspace files,
   ruby-lsp's lazy `Entry#comments` re-parse (`Prism.parse_file_comments`
   has no JS-port equivalent) is replaced by keeping the comments already
   collected in each file's indexing `parseWithMetadata` envelope.
